# 日志与管理员观测平台总体基线

版本：1.5  
基线日期：2026-07-31  
适用范围：Java 正式服务、Python Framework/Worker、Proof、智能问答、知识库、模型配置、测试与正式环境的观测基础设施。  
来源基线：`日志资产审计与建设规划.md` 的源码与环境审计结论，以及本轮已经确认的留存、权限、隔离和前端接入规则。

冻结说明：1.5 的总体架构不再扩写。实现语义、DDL 和契约测试统一由 `07-实现任务与DDL契约测试清单.md` 承接；其中模型 invocation 的 dispatch 口径是对下文“真实尝试”简称的最终解释。

## 1. 本文档的定位

本文档是后续日志、事件、审计、追踪和管理员数据面板的统一基线。它解决两个问题：

1. 当前已经记录了什么、缺少什么、分别处于什么状态；
2. 以后每增加一个功能，相关记录必须写入哪个固定位置。

“不为每个新功能单独建日志表”不代表禁止增加业务表。新功能如果产生新的业务实体、结果、版本或受控内容，可以建立业务表；但请求日志、状态事件、模型调用、安全审计、运行错误、追踪和指标必须优先接入本文规定的固定账本或观测系统。

## 2. 当前确定结论

当前系统已经有较完整的局部记录，但尚未形成统一观测平台：

- `[现有]` Java 有 HTTP 操作审计 `sys_log`。
- `[现有]` Java 合同审查及其他模块有业务结果、状态和人工动作表。
- `[现有]` Python TaskManager 有持久化任务、运行、阶段、事件、制品和条目表。
- `[现有]` Python 合同回调表能够记录协议交互和回调结果。
- `[现有]` Java、Python、容器均有普通文本日志，但格式、脱敏、集中检索和留存不统一。
- `[已本地修改未推送]` Python `tuge_task_event` 已在本地分支补充常用查询索引并通过相关测试，但没有推送或部署。
- `[已确定待开发]` 通用 Java 业务事件账本、模型调用事件账本和 Java/Python 安全审计账本。
- `[已确定待开发]` Java Outbox/Inbox、Python 幂等消费、事件注册表、ScopeResolver 和跨源 QueryCoordinator。
- `[规划]` 每个环境独立的 Loki、Tempo、Prometheus 及其采集器。

当前最高风险：

1. Java Logback 实际写入容器内 `/logs`，Compose 挂载路径为 `/app/logs`，滚动文件未进入持久卷，容器重建后可能丢失。
2. Docker `json-file` 缺少统一轮转限制，可能持续占用磁盘。
3. 普通日志尚未统一结构化和字段级脱敏，可能出现敏感信息泄露。
4. Java → Python → Worker → 模型/工具 → 回调尚无统一 Trace。
5. 模型调用和安全事件缺少跨功能复用的正式事件账本。

## 3. 六类数据必须分开

| 数据类别 | 回答的问题 | 权威去向 | 不应保存的内容 |
|---|---|---|---|
| 业务数据 | 系统最终产生了什么业务结果 | 现有或新增业务表、受控制品库 | 与业务无关的运行堆栈 |
| 业务事件账本 | 谁在何时对哪个对象做了什么、状态如何变化 | Java `biz_business_event`；Python任务使用 `tuge_task_event` | 合同全文、完整问答内容 |
| 安全审计 | 谁访问、导出、越权、修改配置或触发敏感操作 | Java/Python `*_security_audit_event` | 密钥、Cookie、完整认证头 |
| 应用运行日志 | 哪段代码、依赖或容器发生了什么 | JSON/stdout → Alloy → Loki | 原始合同、完整提示词和模型回答 |
| 分布式追踪 | 一次请求经过哪些服务，各层耗时多久 | OpenTelemetry → Tempo | 请求/响应正文 |
| 指标与告警 | 错误率、延迟、容量和 SLO 是否异常 | Prometheus → Grafana/Alertmanager | 用户级原始内容 |

同一操作可以进入多个类别，但每个落点承担不同职责。例如“用户导出合同报告”应记录：

- `sys_log`：HTTP 请求元数据；
- `sys_security_audit_event`：敏感导出行为；
- 现有业务表：导出任务和结果；
- Loki：程序执行异常；
- Tempo：跨服务耗时；
- Prometheus：导出成功率和耗时分布。

不得把同一份正文或大段 JSON 复制到所有存储中。

## 4. 固定落点：以后新增功能必须优先复用

### 4.1 Java / MySQL

#### A. `sys_log` — 管理操作审计 `[现有，需收窄职责]`

职责：

- 记录管理员执行的新增、修改、删除、发布、审批等需要追责的操作。
- 普通只读 API 访问、状态码和耗时写 JSON stdout → Loki；吞吐和延迟写 Prometheus；分层耗时写 Tempo，不能让所有 HTTP 请求同步写 MySQL。

补强要求：

- 增加或统一 `request_id`、`trace_id`、`tenant_id`、`user_id`、`service_version`、`outcome`、`occurred_at`、`ingested_at`。
- 请求参数只保存白名单字段或脱敏摘要。
- 禁止保存 Authorization、Cookie、密码、密钥、完整合同文本、完整提示词、模型完整回答和文件字节。

不承担：

- 业务状态历史；
- 模型调用明细；
- 运行堆栈；
- 分布式调用树。

#### B. `biz_business_event` — 通用 Java 业务事件账本 `[已确定待开发]`

所有 Java 业务模块共同使用，不为“合同、知识库、问答、用户、模型配置”等分别建立日志事件表。

建议核心字段：

| 字段 | 含义 |
|---|---|
| `event_id` | 全局唯一事件 ID |
| `occurred_at` | 事件发生时间 |
| `ingested_at` | 本账本实际收到并落库的时间 |
| `schema_version` | 事件结构版本 |
| `idempotency_key` | 同一业务事实的幂等键 |
| `domain` / `module` | 业务域与模块 |
| `aggregate_type` / `aggregate_id` | 业务对象类型与 ID |
| `event_type` | 稳定事件名称，如 `CONTRACT_REVIEW_CREATED` |
| `old_status` / `new_status` | 状态变化，没有则为空 |
| `tenant_id` / `actor_id` / `actor_type` | 租户和操作者 |
| `request_id` / `trace_id` / `task_id` / `run_id` | 跨层关联字段 |
| `outcome` / `error_code` | 执行结果和稳定错误码 |
| `metadata_json` | 小型、脱敏、可演进的附加元数据 |
| `service_name` / `service_version` | 生产者信息 |

约束：

- 追加写入，不通过更新覆盖历史。
- 事件类型使用稳定的全大写枚举；展示文案由前端或字典层映射。
- 业务结果仍保存在业务表；事件表只记录事实、变化和关联信息。
- `metadata_json` 设置大小上限；字段必须来自事件注册表，不能由生产者任意写入。

#### C. `sys_security_audit_event` — Java 安全审计账本 `[已确定待开发]`

记录：

- 登录、登出、认证失败、权限拒绝；
- 跨租户查询、管理员提权行为；
- 敏感详情查看、文件下载、数据导出；
- 私密模式开关、模型配置修改、凭据引用变更；
- 权限、角色、租户和审计策略修改；
- 发布、配置变更及审计数据清理。

建议字段：

`event_id`、`occurred_at`、`ingested_at`、`schema_version`、`category`、`action`、`outcome`、`risk_level`、`tenant_id`、`actor_id`、`subject_type`、`subject_id`、`source_ip`、`user_agent_hash`、`request_id`、`trace_id`、`reason_code`、`metadata_json`、`service_version`。

安全审计只保存元数据和摘要，绝不保存密钥或敏感正文。

安全审计必须具备防篡改边界：正常应用账号仅有 INSERT、无 UPDATE/DELETE；查询服务使用只读账号；到期清理使用独立 retention 账号。清理、修复、重放、归档和权限变更本身都产生安全事件。正式环境启用数据库审计/binlog，并评估周期性对象存储归档或哈希链；备份留存不得短于审计留存要求，普通业务管理员不能直接操作审计表。

#### D. 现有 Java 业务表 `[现有，继续使用]`

合同任务、结果、风险项、证据、人工操作、知识库文件、问答会话等现有业务表继续作为业务事实来源。只有新功能产生新的业务实体时才新增业务表。不要为了管理员面板方便查询而复制一套“日志业务表”。

#### Java 可靠写入：业务事务 + Outbox/Inbox `[已确定待开发]`

只写业务表再“尽力写事件/调用 Python”会造成事实不一致。凡是 Java 本地业务状态变更并触发跨服务命令，必须采用：

```text
同一个 MySQL 事务
├─ 更新业务表
├─ 插入 biz_business_event
└─ 插入 integration_outbox
事务提交
→ Outbox Dispatcher 带 command_id / idempotency_key 投递 Python
```

Python 回调 Java 时使用 `callback_event_id` / `idempotency_key`。Java 通过 `integration_inbox`，或在现有回调表增加等价唯一约束，在同一事务中完成去重、业务终态和业务事件写入。Outbox/Inbox 是共享的可靠消息基础设施表，不是功能专属日志表。

必须定义：投递状态、租约、重试次数、下次重试时间、死信原因、负载版本、唯一键、过期/归档策略；Dispatcher 可重试，但消费方处理必须幂等。

#### F. `tuge_model_invocation_event` — 通用模型调用账本 `[已确定待开发]`

所有 Python 模型调用功能共同使用，包括合同审查、智能问答、知识库处理、Proof、私密模式和后续 Agent。

采用“一个尝试对应多条生命周期事件”的追加式语义：

- `logical_call_id`：一次业务语义上的模型调用；
- `invocation_id`：一次进入本地执行器或外部 Provider 调度边界的尝试；是否已形成实际请求由 `dispatch_status` 判断；
- `event_id`：这次尝试的一条生命周期事件；
- `attempt_no`：逻辑调用中的尝试序号。

输入 Guardrail、凭据缺失、路由/隐私策略拒绝发生在调度边界前，不创建 `invocation_id`。进入边界后的重试、结构修复和降级产生新的 invocation，并记录 `NOT_DISPATCHED | DISPATCHED | DISPATCH_UNKNOWN`。

生命周期事件：

- `MODEL_INVOCATION_STARTED`
- `MODEL_INVOCATION_DISPATCHED`
- `MODEL_INVOCATION_DISPATCH_UNKNOWN`
- `MODEL_INVOCATION_SUCCEEDED`
- `MODEL_INVOCATION_FAILED`
- `MODEL_INVOCATION_VALIDATION_FAILED`
- `MODEL_INVOCATION_OUTPUT_GUARDRAIL_REJECTED`
- `MODEL_INVOCATION_OUTCOME_UNKNOWN`
- `MODEL_INVOCATION_ABANDONED`

建议字段：

`event_id`、`event_type`、`schema_version`、`logical_call_id`、`invocation_id`、`attempt_no`、`dispatch_status`、`fallback_from_invocation_id`、`occurred_at`、`ingested_at`、`tenant_id`、`user_id`、`feature_code`、`task_id`、`run_id`、`stage_id`、`request_id`、`trace_id`、`provider`、`provider_request_id_hash`、`model_pack_id`、`model_pack_version`、`model_name`、`deployment_name`、`provider_region`、`privacy_mode`、`route_type`、`model_config_id`、`input_token_count`、`output_token_count`、`latency_ms`、`time_to_first_token_ms`、`outcome`、`error_code`、`retry_reason`、`cost_amount`、`cost_currency`、`cost_source`、`pricing_version`、`cost_calculated_at`、`service_version`、`metadata_json`。

其中：

- `privacy_mode`：`STANDARD` / `PRIVATE`；
- `route_type`：`LOCAL` / `EXTERNAL`；
- 凭据只记录无业务含义的 `model_config_id`；确需稳定指纹时使用服务端 HMAC，不能使用可枚举值的普通哈希；
- 业务调用量按去重后的 `logical_call_id`；调度尝试量按 invocation；已确认实际请求量只统计 `dispatch_status=DISPATCHED`，`DISPATCH_UNKNOWN` 单列；
- 同时提供逻辑调用成功率和尝试成功率；重试率按一个逻辑调用是否包含多个尝试计算。

追加式事件表是审计来源，不直接承担“一行一个调用”的列表和大规模聚合。新增可重建的 `tuge_model_invocation_projection` 投影：一行对应一个 invocation，保存 dispatch 状态、开始、终态、Token、耗时、TTFT、成本和模型维度；模型列表与摘要查询投影，详情查询生命周期事件。

投影显式拆分：`lifecycle_status=RUNNING|TERMINAL`；`outcome` 在 RUNNING 时为空，只在 TERMINAL 时取 `SUCCESS/FAILURE/.../UNKNOWN/ABANDONED`。`UNKNOWN` 是 reconciliation 后“最终结果无法确认”的终态，不能表示正在执行。统计中运行中尝试单独计入 active count，不进入终态成功率分母。

Worker 在 STARTED 后崩溃时，由 reconciliation 定时任务依据超时和租约状态追加事件 `MODEL_INVOCATION_OUTCOME_UNKNOWN`（投影 `outcome=UNKNOWN`）或事件 `MODEL_INVOCATION_ABANDONED`（投影 `outcome=ABANDONED`），并同步投影。事件名称与 outcome 值不是同一枚举，Java、Python 和数据库均按该映射实现。数据库至少约束：

- `event_id` 唯一；
- `(logical_call_id, attempt_no)` 在 invocation 投影中唯一；
- 一个 invocation 最多一个 STARTED 和一个终态；
- 终态时间不得早于 STARTED；
- `fallback_from_invocation_id` 不得指向自身；
- reconciliation 可重复执行且不会重复追加终态。

明确禁止：

- API Key、密钥文件内容、完整凭据引用；
- 完整 Prompt、合同正文、附件内容；
- 模型完整回答、完整 Tool 参数；
- 未脱敏个人信息。

如需质量抽检内容，必须建立独立、加密、短期、严格授权的业务样本库，不能塞进本表。

#### G. `tuge_security_audit_event` — Python 安全审计账本 `[已确定待开发]`

记录 Python 服务独立执行的安全敏感行为：

- 内部 Token 验证失败；
- 租户边界拒绝；
- 私密模式路由与本地/外部模型选择；
- 文件/制品读取和下载；
- 模型凭据缺失、选择、拒绝或策略违规；
- 管理员查询、导出和跨租户访问。

Java 接口层和 Python 执行层可以各写一条安全事件，通过 `request_id`/`trace_id` 关联；不能相互替代。

安全事件必须支持 `scope_type=TENANT|SYSTEM`。内部 Token/认证失败、匿名请求、服务身份异常和尚未解析出租户的拒绝允许 `tenant_id`、actor id 或 subject 为空；actor type 支持 `USER/SERVICE/SYSTEM/ANONYMOUS/UNKNOWN`。上下文缺失时必须记录 `missing_context_reason`，不能用空对象掩盖。

#### H. Python 现有业务表 `[现有，继续使用]`

合同回调、Proof Run、线程/消息、知识库文件和其他业务表继续保存业务事实。TaskManager 事件不得替代最终业务结果，业务表也不得替代任务执行历史。

### 4.3 平台观测存储

#### I. Loki — 集中运行日志 `[规划]`

Loki 是集中保存和检索结构化/文本运行日志的服务，不是业务数据库，也不执行模型。

每个环境部署独立链路：

```text
Java / Framework / Workers / Proof / 其他容器
                    ↓ stdout(JSON)
             Alloy 日志采集器
                    ↓
              Loki-test 或 Loki-formal
                    ↓
         Java 管理员聚合接口 / Grafana
```

测试和正式必须使用独立容器、网络、卷/对象存储、写入凭据和查询凭据。除明确允许的本地大模型服务外，两个环境不得互通。

租户相关 JSON 日志与 Span 至少携带 `tenant_id`、`request_id`、`trace_id`、`task_id`、`run_id` 和 `scope_type=TENANT|SYSTEM`。Loki Label 只使用 `environment`、`service`、`container`、`level`、`logger` 等低基数字段；租户和关联 ID 保存在 JSON 字段中，不能作为 Label。历史上没有可靠 `tenant_id` 的日志或 Trace 只允许系统管理员查看，不能根据 taskId 猜测租户。

#### J. OpenTelemetry + Tempo — 分布式追踪 `[规划]`

OpenTelemetry 负责生成和传播 Trace/Span，并采集各层耗时；Tempo 负责保存调用链。

接入会增加中间件和客户端埋点，但不得改变业务状态、调度、合同结果和模型输出：

- 异步批量导出、有界队列；
- 采集失败必须 fail-open，不能阻塞业务；
- 配置开关和采样率；
- 不采集请求/响应正文；
- 同步 Java → Python 接收段可以保持父子 Span；进入队列后保存上游 Trace Context；
- Worker 执行和回调分别创建新的 Trace，并通过 Span Link 关联上游 Trace；
- 数分钟或数小时的异步业务链以 `task_id` / `run_id` 为主关联键，不能强制维持一条超长 Trace；
- 先在测试环境验证，再决定正式启用。

#### K. Prometheus + Grafana/Alertmanager — 指标和告警 `[规划]`

记录吞吐、错误率、延迟分位数、队列深度、Worker 数量、重试、模型调用、数据库连接和容器资源。指标标签不得使用用户 ID、taskId、文件 ID 等高基数字段。

## 5. 新功能记录路由表

以后每个新功能逐项对照；一项操作可能命中多行。

| 新功能产生的信息 | 固定写入位置 | 示例 |
|---|---|---|
| 普通 HTTP 访问、状态和耗时 | JSON stdout → Loki；Prometheus；Tempo | 路由、方法、耗时、状态 |
| 需追责的 Java 管理操作 | `sys_log` | 新增、修改、删除、发布、审批 |
| Java 业务状态变化/用户业务动作 | `biz_business_event` | 任务创建、状态迁移、人工确认 |
| Python 任务、Run、Stage、Tool、Artifact 过程 | `tuge_task_event` | Stage 开始/完成、工具失败 |
| 一次真实模型请求/重试/降级的生命周期 | `tuge_model_invocation_event` | logical call、invocation、STARTED/终态、Token、耗时 |
| 身份、权限、跨租户、私密模式、配置、敏感查看/导出 | 本服务的 `*_security_audit_event` | 权限拒绝、跨租户查询、模型配置修改 |
| 异常、堆栈、依赖与容器运行消息 | stdout JSON → Loki | 数据库超时、HTTP 502 |
| 跨服务调用关系和耗时 | OpenTelemetry → Tempo | Java→Framework→Worker→模型 |
| 计数、比率、容量、SLO | Prometheus | 错误率、P95、队列深度 |
| 业务结果、正文、附件、最终报告 | 现有或新增业务表/制品库 | 合同报告、问答消息 |

### 5.1 允许新建“日志/事件表”的例外

只有同时给出工程证据并完成架构评审时，才允许新增日志或事件表：

1. 写入方处于不同数据库/服务事务边界，无法可靠写入既有账本；
2. 数据的权限、加密、留存或合规要求与既有账本实质不同；
3. 数据量和查询模型实质不同，既有表无法通过分区/索引解决；
4. 该数据其实是新业务实体或业务结果，而不是日志。

`tuge_model_invocation_event` 属于第 2、3 类例外：调用量、成本统计、模型维度、重试粒度和安全限制与普通任务事件不同。

不构成例外的理由：

- “前端查询方便”；
- “这个功能名字不同”；
- “JSON 字段不够用”；
- “先建一张表以后再统一”。

## 6. 统一字段与命名

### 6.1 必须贯穿的关联字段

| 字段 | 产生位置 | 用途 |
|---|---|---|
| `request_id` | 最外层 API 网关/Java | 单次 HTTP 请求 |
| `trace_id` / `span_id` | OpenTelemetry | 一段同步或执行调用链；异步段通过 Span Link 关联 |
| `tenant_id` | 鉴权上下文 | 租户隔离 |
| `user_id` / `actor_id` | 鉴权上下文 | 操作者 |
| `task_id` / `run_id` / `stage_id` | 任务系统 | 异步执行关联 |
| `review_id` / `contract_id` / `file_id` | 业务层 | 业务对象关联 |
| `logical_call_id` | 模型调用层 | 一次业务语义上的模型调用 |
| `invocation_id` | 模型调用层 | 单次真实模型尝试 |
| `occurred_at` / `ingested_at` | 生产者/账本 | 实际发生时间和观测系统接收时间 |
| `service_name` / `service_version` / `environment` | 部署信息 | 定位版本和环境 |

空值允许，但只要该层已知就必须继续透传。关联 ID 不能放进 Prometheus 标签。

### 6.2 事件命名

- 使用 `DOMAIN_OBJECT_ACTION`，例如 `CONTRACT_REVIEW_CREATED`、`KNOWLEDGE_FILE_INDEX_FAILED`。
- 开始和终态分开记录，不覆盖历史。
- `outcome` 统一使用 `SUCCESS`、`FAILURE`、`DENIED`、`CANCELLED`、`TIMEOUT`、`PARTIAL`。
- `error_code` 使用稳定机器码；事件只保存 `display_code` 和登记过的展示参数，展示模板可以更新，但机器码不随文案变化。

### 6.3 事件注册表

所有事件在投产前必须登记，不能把 `metadata_json` 当成任意 JSON：

| 字段 | 要求 |
|---|---|
| `event_name` / `schema_version` | 唯一标识一版事件结构 |
| `producer` / `owner` | 生产服务和责任人 |
| `required_metadata` / `allowed_metadata` | 必填及允许字段；未登记字段拒绝或丢弃并告警 |
| `sensitivity` | 元数据、脱敏、受限等级 |
| `display_code` / `display_template` | 安全展示文案，不直接展示原始异常 |
| `retention` | 继承公共策略或登记例外 |
| `idempotency_strategy` | 事件唯一键和重试行为 |

事件接口返回 `displayCode` 和受限 `displayArgs`；`displayMessage` 仅在服务端按模板生成、脱敏和截断后可选返回。只有运行日志可以返回脱敏后的 `message`。

### 6.4 时间、快照与跨源分页

- 数据库存 UTC 时间，接口返回 ISO 8601 并带时区。
- 所有持久事件同时保存 `occurred_at` 和 `ingested_at`，用于处理晚到事件和时钟偏差。
- 第一页冻结 `snapshotTo`，并从每个来源取得摄取高水位：`maxIngestedAt + maxSequence/maxEventId`，或者来源原生 Point-in-Time Token。后续页除时间条件外必须受该高水位约束，晚到事件留到下一次新查询，不能插入已冻结结果。
- 跨源固定排序：`occurred_at DESC, source_order DESC, event_id DESC`。

所有列表首次生成结果时必须使用以下确定性排序，后续页不能换排序字段或方向：

| 列表 | 固定排序 |
|---|---|
| Task | `created_at DESC, task_id DESC` |
| Model Invocation | `started_at DESC, invocation_id DESC` |
| Security | `occurred_at DESC, event_id DESC` |
| Runtime Log | `occurred_at DESC, source_tie_breaker DESC`；签名 locator 封装 tie-breaker |
| Trace | `started_at DESC, trace_id DESC` |
| Alert | `started_at DESC, alert_id DESC` |
| Task Timeline | `sequence ASC, event_id ASC` |
| Run Event | `sequence ASC, event_id ASC` |
| Correlation Timeline | `occurred_at ASC, source_order ASC, event_id ASC` |

- 游标包含 `snapshotTo`、`sourceHighWatermarks/PIT`、`filterHash`、`lastSortKey` 和各来源 `sourceCursors`；由服务端签名，并绑定用户、权限、租户范围、筛选条件和失效时间。
- Java QueryCoordinator 从各来源按预算预取并归并。严格分页模式下只要一个选定来源超时，本页只能返回预览数据和 `retryToken`，`nextCursor=null`、`complete=false`；客户端必须重试当前页。不得在来源恢复后把更晚的事件插入下一页，破坏全局排序。
- 非严格 best-effort 模式只能用于明确标记的运维预览，响应必须声明不保证完整性/全局顺序，不能用于导出、审计或统计。
- `cursor` 与 `retryToken` 互斥：cursor 进入下一页；retryToken 重新执行当前未完成页。`complete=false` 时 `nextCursor=null`、`hasMore=null`。
- 高水位只适用于追加式数据。所有会 UPDATE 且参与分页或状态筛选的资源都必须建立短期服务端物化结果清单，至少包括 Task、Model Invocation、Alert，以及包含运行中 Trace 的 Trace 列表。首次严格查询按固定排序冻结有序 ID、可用的 `projectionVersion`、`dataAsOf` 和返回摘要，签发 `querySnapshotId/highWatermarkHandle`；后续页只能读取该清单，不能重新按当前状态筛选。若 Trace 接口改为只返回已结束 Trace，可按追加式来源处理，但必须在契约中明确。
- 冻结列表与实时详情采用不同但明确的语义：列表行表示 `snapshotTo` 时刻冻结的摘要；Task、Model Invocation 和 Trace 详情默认返回请求时的最新投影，并返回 `projectionVersion`、`dataAsOf`。前端发现详情版本与列表版本不同时显示“状态已更新”。本期不提供历史 as-of 详情，也不为追求列表与详情一致而保存全部历史详情版本。
- 交互快照默认 15 分钟、单个快照上限 10,000 条；同一用户在同一环境默认最多 5 个活跃快照。相同用户、Scope、权限、筛选和时间窗在 30 秒内复用快照；创建新快照时优先回收该用户最旧的非导出快照。无法回收或全局容量超限时返回 429 和稳定错误码 `OBSERVABILITY_SNAPSHOT_CAPACITY_EXCEEDED`。
- 快照保存有序 ID、版本和必要的紧凑不可变摘要或分页片段，不能默认把 10,000 条完整 JSON 长期保留在 Java/Python 进程堆内。必须监控活跃数、占用字节、创建/复用/回收/过期次数、清理延迟和容量拒绝，并由周期任务清理过期快照。异步导出使用独立的持久快照预算。
- 原生 PIT、高水位内容、租户范围和筛选信息只能保存在 Java/Python 服务端状态或 Java 签名 cursor 中；Java 调用 Python 的 Query String 只传短期、不可猜测的 `hwm_...` 服务端句柄，禁止传原生 PIT、长 JWT 或明文上下文。浏览器只看到诊断性的 source、maxIngestedAt、dataThrough。
- 普通页面单页最多 100 条；大于 10,000 条的结果必须走异步导出。

## 7. 安全和权限边界

### 7.1 默认只展示元数据

管理员面板默认只展示状态、关联 ID、主体标识、耗时、Token、错误码、模型和服务版本等元数据。

所有日志、事件和追踪禁止保存或返回：

- 密码、API Key、Secret、Authorization、Cookie、Session；
- 合同全文、原始文件字节；
- 完整 Prompt、模型完整回答、完整 Tool 参数；
- 未脱敏姓名、手机号、证件号等个人信息。

### 7.2 租户权限

- 租户管理员：接口不提供可选择的 `tenantId`；如传入其他租户范围，返回 403 并记录租户边界拒绝。
- 系统超级管理员新建跨租户授权时，使用 `tenantScope=CURRENT|SELECTED|ALL`、`selectedTenantIds` 和 `X-Observability-Access-Reason`；同 Scope、权限、原因和筛选摘要的自动刷新可复用短期 `X-Observability-Access-Session`，不得扩展范围。Body 只承载资源筛选条件。
- Java `ScopeResolver` 将 Header 统一归一化为一个 `AccessReasonContext`，供授权、Access Context 签发和安全审计复用；各接口不得自行解析不同位置的原因字段。
- 前端传入的角色、租户 ID 不能作为可信依据。
- Java 负责用户认证、权限和租户范围；Python 内部接口只接受服务身份和签名/内部 Token。
- Python 现有仅依赖 `"admin"` 角色且可取消租户过滤的逻辑，需要改为明确区分 `tenant_admin` 与 `system_admin/super_admin`。
- 游标必须绑定上述有效租户范围；不能拿一个租户的游标切换到另一个租户。
- 所有详情接口按 `(environment, tenant_id, resource_id)` 做对象级授权。无权查看与不存在对外统一返回 404，内部仍写安全审计，防止资源枚举。
- 跨租户列表响应签发一个短期 `accessContext`；详情请求通过 `X-Observability-Access-Context` 传入。Token 绑定用户、权限、原查询租户范围、原因码、环境、筛选摘要和有效期，不绑定某一行。详情时 Java 再验证目标资源 tenant 是否属于该范围，不能从 SELECTED 范围跳到其他租户。

安全事件只记录跨租户、敏感详情、导出创建/下载、权限/模型配置/安全策略修改、认证或租户边界拒绝。普通本租户元数据列表轮询只进入访问日志/指标，不进入安全事件账本，避免自动刷新自我放大。

建议权限：

- `monitor:observability:view`
- `monitor:observability:detail`
- `monitor:observability:sensitive`
- `monitor:observability:export`
- `monitor:observability:cross-tenant`
- `monitor:observability:security`
- `monitor:observability:runtime`
- `monitor:observability:operations`

权限组合规则：统一事件接口不返回安全事件，安全事件只能走专用接口；运行日志需要 `runtime`；服务、告警、存储和系统级总览卡片需要 `operations`。导出必须同时具备 `export`、目标资源原权限和目标租户范围权限，`export` 绝不能提升数据可见性。总览按调用者权限裁剪卡片，租户管理员不能看到全平台基础设施和容量。

### 7.3 内部服务认证

- mTLS 在网关、Service Mesh 或应用 TLS 层强制配置并独立验收；OpenAPI 的 `x-mtls-required` 只用于说明，不会自动启用 TLS。
- Service JWT 短期可复用并绑定 mTLS 服务身份；校验 `iss/aud/exp/nbf`，但不按“一次 jti 只能调用一次”处理。
- Scope Token 由 Java 为每个下游 method/path/queryHash/requestId 单独签发，短 TTL、独立 `jti`；网络重试重新签发 Token并沿用聚合 requestId。流式调用使用专门的 Run 绑定 Token 和最大连接时长。
- Python 校验 Token 中的环境与本实例一致，并记录 jti、调用次数和拒绝原因；Java 并行查询不同 Path 不得互相触发重放拒绝。

## 8. 环境隔离与留存

### 8.1 隔离

测试与正式必须独立：

- Docker 网络；
- MySQL/PostgreSQL/Redis；
- Loki、Tempo、Prometheus、对象存储及持久卷；
- 内部 Token、日志写入凭据和查询凭据；
- 域名、端口和服务发现。

唯一允许按既定方式共享的是本地大模型计算服务；共享模型服务也必须通过环境标识、租户上下文和独立调用凭据防止数据混淆。

环境由部署实例和域名确定，不能由浏览器的 `environment` 查询参数选择：

```text
test-admin.xxx.com   → 测试 Java   → 仅测试数据与观测组件
formal-admin.xxx.com → 正式 Java   → 仅正式数据与观测组件
```

管理员门户“切换环境”本质上切换后端 Origin，并重新执行相应环境认证。任何一个 Java 管理实例都不得同时持有测试和正式数据源凭据。响应保留 `environment` 作为数据来源证明。

共享本地模型服务必须按调用来源将日志、指标和 Trace 分别输出到测试或正式 Collector；不能写入一个共享观测存储，也不能用浏览器参数决定输出目标。

### 8.2 留存

| 数据 | 测试环境 | 正式环境 |
|---|---:|---:|
| 模型调用事件 | 10 天 | 1 年 |
| 安全审计事件 | 10 天 | 2 年 |
| Loki 运行日志 | 10 天 | 180 天 |
| Tempo Trace | 10 天 | 14–30 天 |
| Prometheus 指标 | 10 天或按容量 | 15 个月 |
| 合同/业务事件 | 10 天仅适用于测试副本 | 跟随业务记录生命周期和合规策略 |

清理任务必须可审计，先验证时间边界、批量删除上限和失败重试。不得用一次无范围的大 SQL 清空。

正式建设前必须按“每日事件数 × 平均行字节 × 索引放大 × 留存天数”完成容量预算。模型事件、任务事件和安全事件优先按月或按日分区；清理优先删除到期分区。主查询索引以 `(tenant_id, occurred_at, event_id)` 为基线，关联 ID 使用少量独立索引，禁止为所有字段排列组合建索引。跨租户和 30 天查询设置更严格的扫描预算，并优先使用只读副本或专用查询实例。

## 9. 管理员数据面板的数据路径

前端只调用 Java：

```text
当前环境的管理员前端
   ↓ 当前环境认证、权限、租户范围
当前环境 Java /monitor/observability/*
   ├─→ Java MySQL：sys_log / biz_business_event / sys_security_audit_event / 业务表
   ├─→ Python 内部观测 API：Task / Model / Security / Proof
   ├─→ Loki：运行日志
   ├─→ Tempo：Trace
   └─→ Prometheus：指标与告警
```

Java 是统一鉴权、租户过滤、脱敏和聚合边界。浏览器不得直接访问 Python、Loki、Tempo、Prometheus 或数据库。

Java 内部使用 `ScopeResolver` 固化用户、权限、租户范围和跨租户原因，再由 `QueryCoordinator` 调用各数据源 Adapter。查询经过事件注册表和脱敏器后，使用固定快照及签名游标返回。Java → Python 的内部观测 API 以 `06-Java-Python内部观测接口草案.openapi.yaml` 为契约，使用 mTLS、服务 JWT、签名租户 Scope 和对象级授权。

### 9.1 外部—内部接口必须闭合

| Java 外部能力 | Python 内部来源 |
|---|---|
| Task 列表/详情 | `/tasks`、`/tasks/{taskId}` |
| 全局 Task Event / 单任务时间线 | `/task-events`、`/tasks/{taskId}/timeline` |
| Run Stage / Event / Stream | `/runs/{runId}/stages`、`/runs/{runId}/events`、`/runs/{runId}/events/stream` |
| 模型调用列表/详情/摘要 | `/model-invocations`、`/{invocationId}`、`/model-summary` |
| 模型原始生命周期事件 | `/model-invocation-events` |
| Python 安全列表/详情 | `/security-events`、`/{eventId}` |

每个 Java Adapter 必须有契约测试证明字段、过滤、分页、Scope 和错误码映射；禁止 Java 为生成摘要而全量扫描 Python 事件。

### 9.2 SSE 决策

管理员前端使用 `fetch()` + `ReadableStream` 携带 Bearer Header 读取 SSE，不使用无法稳定设置 Authorization Header 的原生 `EventSource`。统一事件和内部任务事件正式使用 `sequence`。SSE `id:` 的值就是 `eventId`，`Last-Event-ID` 必须提交最后收到的 `eventId`；服务端由 eventId 定位对应 sequence 后恢复，客户端按 `eventId + sequence` 去重，不能把 sequence 当成 Last-Event-ID。Java 到 Python 的内部流使用服务 JWT、Run 绑定 Scope Token 和最大连接时长，并遵守相同语义。

### 9.3 专用查询 DTO

统一事件中心使用 `UnifiedEvent`，其 `source` 只能是 `HTTP_AUDIT/BUSINESS_EVENT/TASK_EVENT/MODEL_EVENT`，不得出现 Security、Runtime 或 `runtimeMessage`；安全页面使用严格的 `SecurityEvent`，运行日志页面使用 `RuntimeLogEntry`。专用 DTO 的关键字段必须 required，不能把 actor、安全风险、container、logger、exceptionType 等全部降级成可选 metadata。

### 9.4 异步导出快照

创建导出时 Java 必须立即持久化 `querySnapshotId`，冻结 `snapshotTo`、各来源内部高水位/PIT、filterHash、授权租户范围、资源所需权限和数据/Schema 版本。Worker 只能按该快照执行；10:00 创建的导出不会因 10:03 晚到、10:05 执行而改变内容。

导出状态和下载接口都重新校验 `export + 原资源权限 + 当前租户范围 + 创建者/允许下载者 + 未过期`。创建时的权限快照用于限制上限，不能覆盖下载时已被撤销的权限。导出查询过滤使用 Event/Task/Model/Security/Runtime/Trace 等专用结构，不复用展示用 `MetadataField`。

## 10. 建设顺序

### 阶段 0：立即修复现有风险

1. 修正 Java `/logs` 与 `/app/logs` 挂载不一致。
2. 为所有容器设置日志轮转。
3. 清理普通日志中的密钥、正文和完整模型内容。
4. 固化测试/正式网络、卷、数据库和凭据隔离。

### 阶段 1：冻结基础语义

1. 固化环境绑定部署，不在接口中按参数切换环境。

## 11. 验收底线

- 任意管理员查询都由后端执行租户过滤，不能仅靠前端隐藏。
- 任意跨租户查询均有安全审计记录。
- 测试和正式管理接口由不同部署实例和域名提供，接口不接受环境切换参数。
- 能用 `task_id` / `run_id` 拼接多个局部 Trace、Java 请求、Python 任务、模型调用、运行错误和回调。
- 业务状态、业务事件和 Outbox 在同一事务中提交；Python 命令与 Java 回调经过幂等和重复投递测试。
- 跨源游标绑定快照、筛选、用户、权限和租户范围；翻页验证无重复、无遗漏。
- 每个来源的摄取高水位/PIT 被固定；晚到事件不会进入后续页；任一来源超时时无正常 `nextCursor`，只能重试当前页。
- retryToken 在所有分页外部接口有明确提交入口并与 cursor 互斥；不完整页的 hasMore 为 null。
- Task、invocation、Alert 和含运行中 Trace 的可变列表通过短期服务端结果清单冻结，状态/结果过滤跨页不会漂移；每个列表使用已经登记的固定排序。
- 事件账本是追加式，重试和失败不会覆盖。
- 模型 logical call、调度尝试、已确认实际请求、调度未知、两种成功率和重试率口径有可重复的统计测试。
- 模型列表一行对应一个 invocation；生命周期详情追加展示；孤立 STARTED 会被 reconciliation 收口。
- RUNNING invocation 的 outcome 为空，不能与终态 `UNKNOWN` 混用；对应未知终态的事件名固定为 `MODEL_INVOCATION_OUTCOME_UNKNOWN`。
- 外部每项 Python 数据能力都有内部接口、专用 DTO 和契约测试，不依赖 Java 全量扫描。
- Security、Runtime、Operations 和 Export 组合权限均有拒绝测试；导出权限不提升原资源可见性。
- 跨租户详情必须携带有效 Access Context；用户、权限、原因、环境或筛选摘要不匹配，或目标资源租户不属于原查询范围时不可访问。
- 安全审计账号权限、清理账号、数据库审计/归档和备份留存经过验收。
- 系统级、匿名和未解析租户的安全事件可以合法表达且有 missing-context reason。
- 三个外部分页时间线固定排序：Task/Run 按 `sequence ASC, eventId ASC`，跨来源关联时间线按 `occurredAt ASC, sourceOrder ASC, eventId ASC`；不能由 Java 循环拉完或静默截断。
- 冻结列表与实时详情分别携带 `projectionVersion/dataAsOf`；详情版本变化时前端提示“状态已更新”，且当前接口不伪装支持 as-of 详情。
- 新建跨租户 Session 时从 `X-Observability-Access-Reason` 归一化原因；自动刷新复用 Access Session，运行日志与导出 Body 不存在重复原因字段。
- Java—Python `highWatermark` 只接受短期 `hwm_...` 服务端句柄；原生 PIT、长 JWT、租户或筛选明文不能进入 Query String。
- 异步导出持久化查询快照，状态和下载重新校验原资源权限。
- Export filter discriminator 对每个 filterType 有明确 mapping；Task/Model 跨租户列表的 tenantId 为契约必填。
- SSE 示例、DTO 和恢复协议统一使用 sequence；SSE id/Last-Event-ID 均为 eventId。
- 快照复用、每用户活跃数、存储字节、回收、过期和容量错误码经过压力与清理测试。
- 日志中扫描不到凭据、认证头、完整合同、完整 Prompt/Response。
- 测试和正式的网络、数据库和观测存储相互独立。
- Loki/Tempo/Prometheus 故障不影响业务主链路。
- 10 天测试留存清理经过边界、失败重试和恢复验证。
- 管理员面板显示的“真实调用”“生产验证”等表述必须有对应环境证据，模拟测试不得冒充。
